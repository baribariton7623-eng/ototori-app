# サービスとして販売するための設計メモ

「レッスン予約」を複数の講師(主催者)に有料で提供する場合の、プロダクト・料金・販売・法務・運用の整理。
技術的な多テナント対応(主催者ごとの公開ページ、プラン上限、Stripe 課金)は実装済み。ここではそれを「売る」ために必要なことをまとめる。

---

## 1. 提供形態

| 形態 | 内容 | 向き不向き |
| --- | --- | --- |
| **SaaS(推奨)** | 自分で 1 つ運用し、講師ごとにアカウントと公開ページ URL を発行。月額課金 | 運用が一元化され、改善が全員に届く。Google 審査も 1 回で済む |
| 買い切り・自己ホスト | コードを渡して各講師や教室が自分で動かす | 講師側に技術力が要る。サポートが個別対応になり収益化しにくい |
| 教室・スクール単位のプラン | 1 契約に複数講師(将来の「組織」機能) | 音楽教室・カルチャーセンター向け。現状は講師=テナントなので拡張が必要 |

まずは SaaS で、講師個人(声楽・ピアノ・語学・パーソナルトレーナー等、1 対 1 レッスンで Google カレンダーを使っている人)を対象にする。

## 2. 料金プラン(実装済みの上限に対応)

| | フリー | プロ |
| --- | --- | --- |
| 月額 | 0 円 | 目安 980〜1,980 円(税込) |
| 月間予約数(レッスン日基準) | 10 件 | 無制限 |
| 連携カレンダー | 1 件 | 無制限 |
| 予約の Google カレンダー自動登録 | なし(参照のみ) | あり |
| キャンセルフィーのカード決済(講師の Stripe に直接入金) | なし | あり |
| 直前変更の承認フロー・3 択申請 | あり | あり |
| 公開予約ページ URL | あり | あり |

- 上限は `src/domain/plans.ts` の `PLAN_LIMITS` で一元管理。金額は Stripe の Price で管理し、コードには持たない。
- フリーで「価値を体験できる」が、本業で使うとすぐ上限に当たる設計(月 10 件 = 週 2〜3 レッスン)。
- 支払い遅延(`past_due`)は Stripe の再請求(Smart Retries)に任せ、その間は自動的にフリー上限に落ちる(`effectivePlan`)。猶予を与えたい場合は `effectivePlan` で `past_due` を `pro` 扱いに変えるだけ。
- 年払い割引、初月無料(Stripe の trial)、紹介コード(Checkout の `allow_promotion_codes` は有効化済み)は Stripe 側の設定で追加できる。

## 3. 課金の仕組み(実装済み)

```
講師 ─「アップグレード」→ POST /hosts/{id}/billing/checkout → Stripe Checkout(サブスク)
Stripe ─ checkout.session.completed / customer.subscription.* → POST /billing/webhook → plan / subscriptionStatus 更新
講師 ─「支払い方法・解約の管理」→ POST /hosts/{id}/billing/portal → Stripe Customer Portal
```

Stripe 側の準備:
1. 商品「プロプラン」と月額の Price を作成 → `STRIPE_PRICE_ID_PRO`
2. Webhook エンドポイント `https://<api>/billing/webhook` を登録し、`checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted` を購読 → `STRIPE_WEBHOOK_SECRET`
3. Customer Portal を有効化(解約・支払い方法変更を許可)
4. `.env` に `BILLING=stripe`, `STRIPE_SECRET_KEY`, `APP_BASE_URL=https://<フロントの URL>`

ローカルは `BILLING=fake` で、アップグレードボタンを押すと即時にプロになる。

### キャンセルフィー決済(Connect)の設計と法務上の位置づけ
- 講師ごとに講師本人名義の Stripe アカウント(Standard)を作ってもらい、決済はそのアカウント上で行う(Direct charge)。販売者・入金先・返金やチャージバックの当事者は講師で、運営者の口座を資金が経由しない。
- 運営者はプラットフォーム手数料(application fee)を取っていない。取る場合は、手数料の性質と表示、収納代行・資金移動業との関係を改めて専門家に確認する。
- Stripe ダッシュボードで Connect を有効化し、「連結アカウント」のイベントを受ける Webhook を `/billing/connect-webhook` に登録する(`checkout.session.completed`, `checkout.session.async_payment_succeeded`, `account.updated`)。その署名シークレットを `STRIPE_CONNECT_WEBHOOK_SECRET` に設定する。

## 4. 立ち上げ前に必要なもの

### Google OAuth の審査(重要・時間がかかる)
提出資料と文案は `docs/google-oauth-verification.md` にまとめた。
- Calendar のスコープ(`calendar.events`, `calendar.readonly`)は **機密スコープ** のため、不特定多数の講師に使わせるには Google の OAuth アプリ審査(ブランド確認 + スコープ審査)が必要。未審査だとテストユーザー 100 人まで・「未確認のアプリ」警告が出る。
- 審査には: 公開されたプライバシーポリシー URL、利用規約 URL、ホームページ、スコープの利用目的説明、デモ動画が要る。**2〜6 週間**見込む。
- 審査前でも、講師をテストユーザーに手動追加すれば少人数のベータ運用はできる。

### 法務・表記
3 ページとも実装済み(`/terms`, `/privacy`, `/tokushoho`)。運営者情報は `web/.env` の `VITE_OPERATOR_*` で差し込み、未設定の項目はページ上に赤字で表示される。**文面はひな形であり法的助言ではない。公開前に専門家の確認を推奨。**
- **特定商取引法に基づく表記**: 事業者名・責任者・所在地・電話・メール・料金・支払時期・提供時期・解約返金。個人事業主は所在地と電話番号を「請求があった場合には遅滞なく開示いたします」とすることもできる。
- **利用規約**: 講師と生徒の間の契約に運営者は関与しないこと、14 日ルールと承認制、キャンセルフィーは講師と生徒で直接精算、有料プランの自動更新と解約、免責(消費者契約法を考慮)。
- **プライバシーポリシー**: 取得情報(カレンダーは予定の時間帯のみで件名等は取得しない)、委託先(Supabase / Google / Stripe / Resend)、Limited Use の宣言、保存期間と退会時の削除。
- インボイス制度: 講師が経費計上するので、適格請求書発行事業者なら Stripe の請求書設定に登録番号を入れる。

### インフラと費用の目安(月)
| 項目 | 目安 |
| --- | --- |
| API サーバー(Render / Fly.io / Railway 等の常駐 Node) | 0〜1,500 円 |
| Supabase(Postgres + Auth) | 0 円(Free)〜3,700 円(Pro, 25 USD) |
| フロント(同一サーバー配信、または Netlify/Cloudflare Pages) | 0 円 |
| ドメイン | 年 1,500〜3,000 円 |
| Stripe 手数料 | 決済額の 3.6% |
| メール送信(通知を実装したら。Resend / SendGrid) | 0〜1,500 円 |

プロ 20 契約(1,480 円)で月商約 3 万円、原価 5 千円前後。50 契約を超えたあたりから Supabase Pro とサポート時間が主なコストになる。

## 5. 販売チャネル

1. **既存の人脈から**: 合唱団・音楽教室のつながりで講師 3〜5 人にベータ利用してもらい、フィードバックと事例を得る(この段階は Google 審査前でも可)。
2. **LP(ランディングページ)+ SEO**: 「レッスン 予約システム 無料」「Google カレンダー 連携 予約 個人」などで検索する講師向けに、フリープランを入口にする。現状の `#/` トップは簡素なので、独立した LP を用意する。
3. **講師コミュニティ**: 音楽・語学講師の SNS コミュニティ、ココナラ・ストアカなどで活動している講師への直接案内。
4. **教室・スクール向け B2B**: 複数講師をまとめて契約したい教室が現れたら「組織プラン」を検討(下記ロードマップ)。

差別化の軸は「**直前キャンセルの承認制と 3 択申請**」。汎用予約ツール(Google カレンダーの予約スケジュール、Calendly 等)は無料で空き枠予約ができるが、直前キャンセルのルール運用(事情説明・振替・キャンセルフィー)を仕組みとして持っていない。ここを LP の第一メッセージにする。

## 6. 運用

- **サポート**: 問い合わせ先メール(特商法表記にも記載)。よくある質問: Google 連携の手順、カレンダー ID の場所、slug 変更で URL が変わること。
- **監視**: `/health` の外形監視、Webhook 失敗(Stripe ダッシュボードで確認可)、`calendar_error` の発生率。
- **バックアップ**: Supabase の自動バックアップ(Pro)。Free の場合は `pg_dump` を定期実行。
- **データ削除**: 設定画面の「退会」で実装済み。講師の退会では今後の予約を休講扱いにして生徒へ通知し、Stripe を即時解約、Google トークンを失効させてから全データを削除する。
- **メール到達率**: Resend で送信元ドメインの SPF / DKIM を設定する。未設定だと迷惑メール扱いになりやすい。
- **料金改定**: Stripe で新 Price を作り、既存契約は旧 Price のまま(グランドファザー)にするのが摩擦が少ない。

## 7. ロードマップ(売るために優先度が高い順)

| # | 項目 | 状態 |
| --- | --- | --- |
| 1 | 通知メール(予約確定・申請・承認結果・休講) | 実装済み(Resend)。送信元ドメインの DNS 設定が必要 |
| 2 | LP・利用規約・プライバシーポリシー・特商法表記 | 実装済み。運営者情報の設定と専門家確認が必要 |
| 3 | Google OAuth 審査の提出 | 資料作成済み(`docs/google-oauth-verification.md`)。ドメイン取得・動画撮影・提出は運営者の作業 |
| 4 | 退会(データ削除) | 実装済み |
| 5 | 講師による休講と生徒への連絡 | 実装済み(1 件ずつ。一括休講は未対応) |
| 6 | 組織(教室)プラン: 1 契約に複数講師、教室単位の公開ページ | 未着手。データモデル(組織テーブル・講師の所属・請求先)と料金の設計判断が必要 |

| 8 | 前日リマインドメール | 実装済み。外部 cron から毎時叩くか、サーバー内タイマーで実行 |
